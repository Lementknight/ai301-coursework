# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| cause-fits-repro | The plan's stated cause (Diagnosis / Cause), read against the repro evidence block: its numbered steps, every control run (a step that changes one thing and keeps the rest), and its Actual line. A cause cited from a thread comment is read the same way. | Every observation and control in the repro evidence is what the stated cause predicts. Fail if any step or control contradicts it (the bug still happens with the suspected part bypassed or removed, or the suspected part already behaves correctly in a control), or if the repro evidence points at a different component than the plan changes. Unclear only if the repro evidence has no step or control that could confirm or rule out the cause. | required |
| bounded-scope | The plan's scope statement and its list of changes, read against the issue title and the repro's Actual line. | The plan is one bounded change at the place the repro isolates, and it says what it will not touch. Fail if it bundles work the issue never asked for (a refactor, a migration, a new option or setting, a redesign, a second symptom), or if its "won't touch" list contains the thing the repro shows is broken. A fix plus one explicitly deferred follow-up named as not part of this change is still bounded. | required |
| executable | The plan's files or areas, approach, and order of work. | A stranger could start today: it names the specific file, function, or layer to change and the concrete change to make there, and every real decision is made in the plan. Fail if it names no file or area, leaves a choice open ("whichever is easier", "somewhere", "maybe also"), or says to investigate or profile first with no chosen approach. | required |
| decisive-test | The plan's test plan, read against the repro's numbered steps and its Expected line. | The test names an observable outcome that would differ before and after the fix, and it ties back to the repro (the repro steps re-run with the expected result, or a test that encodes the issue's failing case). Manual or automated both count. Fail if it is only "run the test suite", "make sure nothing regresses", "should feel fast", or has no stated expected result. | required |
| thread-and-policy-fit | The plan comment, read against the Thread highlights (any direction from a maintainer or collaborator, any prior-art PR) and the Repo facts block (bug-report template asks, contribution policy, AI-use policy). | The comment engages the maintainer's explicit direction or prior work in the thread instead of ignoring it, and satisfies every stated policy ask. Where the repo states an AI policy that requires disclosure, the comment must disclose AI use in plain words, and a comment with no disclosure fails. Where the repo states no policy and the thread has no direction, this passes. Fail if the comment contradicts or skips a maintainer's direction in the thread, or omits disclosure the policy requires. | required |
| honest-unknowns | The plan's risks / unknowns section and its Deviations heading (live), and the plan comment's wording. | Unknowns the plan actually has (untested platforms, untried cases, assumed behavior) are stated as unknowns, and certainty is claimed only for what the repro shows. Preferred only: a terse plan with no stated unknowns still passes when it claims nothing it hasn't shown. | preferred |

## Verdict rule

Accept only if every required check passes. Reject if any required check fails. An `unclear` on a required check counts as fail. Preferred checks never change the verdict; mention a failed preferred check in the summary only. Grade the plan itself, not its length or polish: a terse plan that passes every required check is accept, and a long confident plan that fails one is reject.
